Making Sense of ASP.NET Core 10 Telemetry with OpenTelemetry and ELK

A page is slow, an API returns 500, or a database call fails. The user sees the symptom, but where do you start looking? A console message might tell you that something went wrong. To understand why, you need to connect that message to the request, its dependencies and the state of the process.

That is the problem we'll work through with MVC_App. The solution has an ASP.NET Core application with MVC, Razor Pages and JSON APIs, a Blazor Server interface, and two console clients. We'll follow a request through the code, see how its telemetry reaches the backend, and use Kibana to investigate it.

One distinction matters from the start: the MVC and Blazor applications send telemetry to ELK. The API console generates traffic for them, while the PostgreSQL console sends its own telemetry to Azure Monitor/Application Insights. Keeping those paths separate will save you from looking for data in the wrong place.

Connection strings and keys in the examples are redacted. Supply your own private configuration when running the solution, and rotate any credentials that have already been shared.

1. What is telemetry?

Telemetry is the information an application produces while it runs: requests handled, time spent waiting, memory used, exceptions raised, and much more. Sending that information outside the process gives you something to investigate after a request has finished—or after the process itself has stopped.

You'll often hear telemetry discussed alongside observability. The distinction is useful: telemetry is the evidence; observability is how well you can use that evidence to understand the system. Monitoring tells you when a known threshold has been crossed. A good set of telemetry also helps you investigate a problem you hadn't anticipated.

The three signals we'll use are logs, metrics and distributed traces. OpenTelemetry, or OTel, provides the APIs, SDKs, instrumentation and Collector that gather and move them. OTLP is the transport protocol. At the other end, ELK—Elasticsearch, Logstash and Kibana—stores, transforms and presents the data. “TEL” simply means telemetry here, not a separate component.

SignalQuestion answeredExample in this solution
LogsWhat event occurred, and with which context?A department conflict, an API-key challenge, a SQL command failure, or a Blazor render exception.
MetricsHow frequently, how slowly, or how much?HTTP duration, runtime memory/GC observations, PostgreSQL employee operation counters and a duration histogram.
TracesWhich operations participated in a request, and where was time spent?A Blazor outgoing HTTP span, the MVC incoming request span and SQL command child spans.

Think of a trace as the story of an operation. Its spans describe the individual steps: an incoming HTTP request, an outgoing API call, or a SQL command. Each span has timing information, attributes and an identifier; related spans share a trace ID. A log written while a .NET Activity is current can carry that same context, giving you a way to move from a message to the request behind it.

Resource attributes answer a different question: which application produced this? In this solution, service.name and deployment.environment.name identify the service and environment. They describe the producer rather than a particular request.

Suppose the API starts returning 500 responses. Metrics show how often it happens. A trace helps locate the failing dependency. Logs explain the error in more detail. Looking at all three is usually more useful than collecting more of just one.

2. Connecting ASP.NET Core 10 to OpenTelemetry

If you've used ILogger<T>, you've already worked with one of the building blocks. .NET also provides System.Diagnostics.Activity and ActivitySource for tracing, and System.Diagnostics.Metrics.Meter for metrics. OpenTelemetry connects these diagnostics to an export pipeline; ASP.NET Core does not send them to ELK on its own.

Both web projects call builder.AddApplicationTelemetry() during startup. The method brings the pieces together in five steps:

  1. Check the configuration. If telemetry is disabled or the endpoint is missing, the method returns without registering this OTel pipeline. Other configured logging providers can still run.
  2. Keep the message and its context. AddOpenTelemetry includes formatted messages and logging scopes. The scopes carry fields such as the response status and error category, so you can filter them without searching message text.
  3. Follow the request and its dependencies. ASP.NET Core instrumentation observes incoming HTTP requests, HttpClient instrumentation observes outgoing calls, and MVC_App adds SqlClient tracing. Propagated W3C context can connect the spans across services.
  4. Collect measurements. HTTP and runtime instrumentation provide metrics. MVC_App also listens to the Kestrel, routing and diagnostics meters; each contributes data when the relevant activity occurs.
  5. Send the signals to the Collector. UseOtlpExporter(OtlpExportProtocol.HttpProtobuf, endpointUri) configures export for logs, traces and metrics. The local base URL is http://localhost:4318; the exporter appends paths such as /v1/traces.

The solution targets net10.0, although these diagnostic APIs span several .NET releases. The important separation is between recording an operation and storing it: an Activity still needs a working exporter and backend before you can inspect it in Kibana.

Why Blazor needs more than HTTP middleware

Blazor adds a wrinkle. After the initial page load, the browser works through a server-side circuit. An exception raised by a later component event may occur long after that first HTTP request has ended. To cover those paths, the project uses incoming request middleware, an outgoing ApiLoggingHandler, and LoggingErrorBoundaryLogger. The middleware skips /_blazor traffic to reduce noise. There is no browser OTel SDK here, so don't expect a complete browser trace or assume every click belongs to the initial page trace.

Why the console projects differ

The API console is useful for generating traffic: it calls the backend and prints timings, while the backend produces the telemetry you'll search in ELK. The PostgreSQL console is a separate example. It creates business activities and metrics, adds Npgsql/runtime/process instrumentation, and exports to Azure Monitor. Because a console run may finish quickly, it explicitly flushes its providers before exiting.

3. Advantages of telemetry with ELK

The payoff comes when you need to investigate something across application boundaries. Instead of switching between consoles and guessing which messages belong together, you can ask focused questions about a service, a request or a failure.

  • Search both web applications in one place. The service identity tells you whether a record came from MVC or Blazor.
  • Filter on meaning, not wording. Stable error categories let you find conflicts, authorization failures and server errors even if their messages change.
  • Follow a reported problem. When context is available, the trace ID returned to an API caller connects the visible error to its request, SQL calls and related logs.
  • Shape the data before indexing it. Logstash turns OTLP batches into searchable records and repairs a legacy field name along the way.
  • See patterns over time. Elasticsearch aggregations and Kibana charts help you compare services, routes, statuses and error categories.
  • Keep backend details out of application code. The application uses OTel APIs; it doesn't need to know the name of an Elasticsearch index.
  • Check the pipeline with known failures. The diagnostic endpoints and workload clients produce predictable events you can trace from request to dashboard.

There is still a system to operate. Telemetry consumes CPU, network capacity and storage, and the data needs access controls and retention rules. This sample gives you the collection path and query examples; alerting, SLOs, browser real-user monitoring and saved dashboards would be separate additions.

Read the architecture in two parts: application calls at the top, telemetry delivery underneath. Only the logs pass through Logstash. Traces and metrics take a shorter route from the Collector to Elasticsearch, while PostgreSQL telemetry goes to Azure Monitor independently.

The web applications run on the development machine. compose.yaml starts the four observability containers on the telemetry bridge network. Inside that network, the Collector and Logstash reach Elasticsearch at http://elasticsearch:9200. The host applications use the published loopback receiver. This difference is easy to miss: localhost inside a container means that container, not the host or another service.

5. Following a request through the code

5.1 An API call from Blazor

Start with a department or employee action in Blazor. The component calls Api/MvcAppApiClient.cs, whose typed HttpClient supplies the API key and runs through ApiLoggingHandler. HttpClient instrumentation can create a client span and pass its trace context to MVC. The backend creates a server span, authenticates the caller and validates the request before reaching the controller's database work.

That work uses CompanyContext. SqlClient instrumentation records database spans, and the custom EF interceptor logs each command's timing and outcome. A single button click can therefore produce several useful records: the outbound call, the incoming request and one or more SQL commands.

The outbound API key authenticates the Blazor server as an API client; it is not the browser user's delegated token. Sharing the Identity database permits the same account credentials in both web applications, but the distinct cookies do not implement shared-session single sign-on.

5.2 A handled conflict and an unhandled fault

Now suppose a department name already exists. The controller raises a domain conflict, and API middleware returns a 409 problem document with an error category and trace ID. That event is logged as Warning, not Error—a useful distinction when you're searching for expected business failures.

The browser MVC flow behaves differently: it redirects to the error page. You may see a 409 in the exception event and a 302 in the final request log, followed by a new request for the error page. Neither record is necessarily wrong; they describe different stages. Unexpected API exceptions follow the 500 path, while an authentication challenge can return 401 without throwing at all.

5.3 SQL telemetry is both logs and spans

DbCommandLoggingInterceptor logs command operation/database/duration and at most 1,000 characters of text. Separately, SqlClient tracing adds db.statement to spans. The filter on Microsoft.EntityFrameworkCore.Database.Command only suppresses that framework category's informational OTel logs; it does not remove command text emitted by the custom interceptor or by span enrichment.

Parameterized commands do not export parameter values through this interceptor, but raw SQL literals and provider exception messages still need scrutiny. Logs inherit whichever Activity is current when they are emitted. Trace-level correlation is useful; do not assume an EF post-execution callback always retains the SQL span as its current Activity.

5.4 PostgreSQL business measurements

AppDiagnostics defines employee.operations, employee.rows.affected, employee.rows.read, employee.operation.failures, and the millisecond histogram employee.operation.duration. Observable gauges report table rows, active rows and salary total from the latest snapshot. These are domain measurements, not merely HTTP/runtime metrics. The repository wrapper records outcome/duration and adds SQLSTATE on PostgreSQL errors. Npgsql supplies command-level spans; the workload adds scenario/command activities around them.

These PostgreSQL observations are visible through Azure Monitor, not through the local mvcapp-logs-* view. Azure Monitor's traces table can contain application log records; that name should not be confused with OTel distributed spans. Azure's Kusto Query Language and Kibana Query Language both use “KQL” but are different languages.

6. YAML and configuration, explained

6.1 compose.yaml: the local infrastructure

Before starting Docker, allow enough memory for the stack. These four container limits add up to about 4.25 GB, before the applications, databases, Docker itself and the host OS. The table shows the pinned image versions; check their availability in your environment. The optional MVC Dockerfile is separate from this Compose setup.

There is no Filebeat or Elastic APM Server service. Logstash tails the Collector output directly. No named Elasticsearch data volume is declared, so this is not a managed durable-storage design. Depending on the image, anonymous storage may exist; do not rely on container recreation to preserve or reattach your data. The explicitly named logstash-data volume stores input offsets, not the Elasticsearch documents.

6.2 observability/otel-collector.yaml: one receiver, three routes

  • Receiver: otlp.protocols.http.endpoint: 0.0.0.0:4318 listens within the container. Compose restricts host access to loopback. OTLP gRPC/4317 is not configured.
  • Memory limiter: checks every second with limit_mib: 192 and spike_limit_mib: 48. It can refuse data under pressure; a container memory limit is not a lossless-delivery guarantee.
  • Batch: timeout: 5s and send_batch_size: 512 reduce exporter overhead. Send batch size is a trigger, not a configured hard upper bound; there is no send_batch_max_size here.
  • Elasticsearch exporter: requires data streams, allows OTel/ECS mapping modes, queues up to 256 export requests and retries a limited number of times. No persistent queue storage is configured. Default stream names are retained to match built-in OTel templates; actual streams should be discovered rather than assumed.
  • File exporter: writes one OTLP JSON export envelope per line to /otel-output/logs.jsonl. Rotation uses 10 MB, three days and three backups. One line can contain many log records.
  • Pipelines: traces and metrics use the Elasticsearch exporter; logs use only file/logs. Adding an exporter definition alone does not route data to it: the pipeline's exporter list makes that choice.

Do not take the commented logs_index example as an active setting. This Collector's log pipeline does not use its Elasticsearch exporter at all. The custom daily log-index name is configured in Logstash, while trace and metric streams follow the Collector exporter's compatible naming.

6.3 observability/logstash/pipeline/otel-logs.conf: from envelopes to events

  1. The file input watches /otel-output/logs*.jsonl*, including rotated files. It starts new/untracked files at the beginning and stores offsets at /usr/share/logstash/data/sincedb-otel-logs.
  2. The json codec parses each already separated line. json_lines would wait for delimiters that this input has already removed.
  3. Ruby traverses resourceLogs → scopeLogs → logRecords and decodes OTLP AnyValue strings, numbers, booleans, arrays and key-value lists. Unsupported representations such as bytesValue are not handled by this helper and become nil.
  4. It constructs a fresh small event for each record rather than repeatedly deep-copying the entire envelope with nested split filters. This keeps fan-out memory usage much more manageable.
  5. It copies message/severity, trace_id/span_id, resource_attributes/log_attributes, service_name, deployment_environment and scope_name. Nanosecond epoch timestamps are converted to Logstash timestamps via a floating-point seconds conversion, so this is not exact nanosecond preservation.
  6. It rewrites the legacy http.route.matched attribute to http.route_matched. Otherwise Elasticsearch could need http.route to be both a scalar string and an object, rejecting documents.
  7. It cancels the original envelope and indexes the emitted records into mvcapp-logs-%{+YYYY.MM.dd}.

The file hand-off has limits. Resetting sincedb can replay old records, and without deterministic document IDs those replays create duplicates. If Logstash falls behind for long enough, rotation can remove logs before they are read. There is no persistent Logstash queue configured here. Treat observability/otel-output as runtime data, and keep its JSONL files private: they may contain SQL text or personal information.

6.4 Application, project and container configuration

Base appsettings.json files define logging, database connections and application credentials. Development files set the web OTLP endpoint and distinct service names. The custom extension explicitly reads endpoint/name/enable keys from IConfiguration; that does not mean every standard SDK environment variable is automatically read from JSON. In particular, set OTEL_METRIC_EXPORT_INTERVAL as an actual process environment variable when controlling the SDK reader interval unless explicit binding is verified.

launchSettings.json supplies local URLs/environment for IDE or dotnet-run profiles. It is not production deployment configuration. The .csproj files in the solution define target frameworks and package dependencies. .dockerignore excludes appsettings and local launch settings, so a Docker deployment must inject those settings externally.

If older setup notes describe a different route for logs, check the current Compose and pipeline files. The configuration shown here sends logs through Logstash and persists its read offsets in the named volume.

7. Kibana KQL queries and dashboard panels

7.1 Create the data view

  1. After starting the applications and generating traffic using section 8, open http://localhost:5601.
  2. Open Data Views under Stack Management (or create a data view from Discover, depending on the Kibana navigation). Enter mvcapp-logs-* as the index pattern and choose @timestamp as the time field.
  3. Open Discover, select that data view, and select KQL in the query-language selector—not Lucene or ES|QL.
  4. Set the time picker to Last 15 minutes, or an absolute range covering the test. Enable a modest auto-refresh interval such as 10 seconds during a demonstration.
  5. Add service_name, severity_text, message, trace_id, scope_name and relevant log_attributes fields as columns. Inspect an actual document before choosing aggregation fields.

7.2 Copy-ready Kibana KQL examples

Paste one query at a time into Discover or a dashboard panel's KQL filter. KQL selects the documents; Lens turns those results into aggregations and charts. These filters use the fields written by the Logstash pipeline. Check those fields in your own index before building panels, and remember that Kibana KQL is different from Azure's Kusto Query Language.

QuestionKQL filterInterpretation
1. What are both web services logging?
service_name : ("MVC_App" or "MVC_App.BlazorClient")
All matching events, including framework, SQL and application logs—not a request count.
2. Which MVC API requests completed?
service_name : "MVC_App" and scope_name : "MVC_App.Middleware.RequestLoggingMiddleware" and log_attributes.http.request.is_api : true
Use this as the base filter for API request/status panels. Escaping exceptions can produce a last-chance failure record from the same middleware.
3. Which API requests returned 5xx?
service_name : "MVC_App" and scope_name : "MVC_App.Middleware.RequestLoggingMiddleware" and log_attributes.http.request.is_api : true and log_attributes.http.response.status_code >= 500
Includes 500 and 503; does not rely on one error-category flag.
4. Which API requests were unauthorized or forbidden?
service_name : "MVC_App" and scope_name : "MVC_App.Middleware.RequestLoggingMiddleware" and log_attributes.http.request.is_api : true and log_attributes.http.response.status_code : (401 or 403)
Includes challenges that did not throw an exception.
5. Which exceptions were actually recorded?
log_attributes.error.type : *
Application-classified exception events. Not every framework/SQL exception record necessarily has this custom field.
6. Where are domain conflicts occurring?
service_name : "MVC_App" and scope_name : "MVC_App.Middleware.ExceptionHandlingMiddleware" and log_attributes.error.category : "conflict"
Uses the exception event rather than counting both the exception and completion logs.
7. Which 404s were unmatched routes?
scope_name : "MVC_App.Middleware.RequestLoggingMiddleware" and log_attributes.http.response.status_code : 404 and log_attributes.http.route_matched : false
The URL did not select an endpoint.
8. Which 404s occurred on matched routes?
scope_name : "MVC_App.Middleware.RequestLoggingMiddleware" and log_attributes.http.response.status_code : 404 and log_attributes.http.route_matched : true
Inspect the associated exception: missing data and deliberately injected errors can both appear here.
9. What happened during one trace?
trace_id : "REPLACE_WITH_THE_REPORTED_TRACE_ID"
Replace the placeholder with a real trace ID from a problem response or log, then sort by timestamp ascending.
10. Which SQL commands took over 100 ms?
service_name : "MVC_App" and scope_name : "MVC_App.Data.DbCommandLoggingInterceptor" and log_attributes.db.duration_ms > 100
One SQL command is not one HTTP request. This field measures command duration in milliseconds.
11. Which Blazor outbound API calls were slow?
service_name : "MVC_App.BlazorClient" and log_attributes.http.request.direction : "outbound" and log_attributes.http.client.duration_ms > 1000
Calls taking over one second, including slow failures. This is client-observed duration, not server-only execution time.
12. Which outbound API calls were unavailable?
service_name : "MVC_App.BlazorClient" and log_attributes.http.request.direction : "outbound" and log_attributes.error.category : "service_unavailable"
Can represent a real HTTP 503 or a transport failure classified as 503 by ApiLoggingHandler.
13. Which Blazor sign-ins failed?
service_name : "MVC_App.BlazorClient" and log_attributes.event.category : "authentication" and log_attributes.event.action : "sign_in" and log_attributes.event.outcome : "failure"
Inspect auth.failure_reason. Treat user.name as personal data, not a public dashboard label.
14. What was logged for a deliberate 503 test?
service_name : "MVC_App" and log_attributes.url.path : "/api/diagnostics/unavailable"
Useful for checking a known test case. Multiple events can describe the same request.

resource_attributes.service.name is also retained, but the pipeline makes service_name convenient. A bare error.type is not the same field as log_attributes.error.type. The top-level log correlation key is trace_id; trace data-stream schemas can differ, so inspect their mappings before attempting cross-view searches.

Use numeric status filtering for all 5xx. error.is_server_error is based on the exact mapped category; 503 uses service_unavailable. A severity Error filter also omits expected 400/404/409 failures logged as Warning and can include non-request failures. Exception existence, HTTP failure and severity are related but different questions.

For an HTTP completion dashboard, filter to scope_name : "MVC_App.Middleware.RequestLoggingMiddleware" before counting requests. Otherwise SQL, framework, outbound-call and exception events inflate the count. Keep domain-error dashboards separate from final wire-status dashboards, especially for MVC redirects. Prefer framework HTTP duration metrics or suitable span measurements for request latency; the custom request logs do not uniformly provide a duration field.

Useful panels include completion counts by status, domain errors by category/type, failures by service, unmatched routes, and slow SQL command logs. Traces and metrics require their own discovered data streams/views. This stack does not guarantee that raw OTel data streams automatically populate every Elastic APM UI feature.

8. Run the solution and generate some telemetry

With the collection path clear, it's time to put traffic through it. You'll need Docker, the .NET 10 SDK and your own database connections. Use a training database: several optional scenarios deliberately insert, update and delete rows. Start with the diagnostic requests and read-only workloads before trying those write paths.

The commands use PowerShell 7.1 or later (pwsh) so credentials can be entered with masked input. Run them from the solution root; adjust the first path to match your checkout. 8.5 Generate predictable telemetry without business-data writes — terminal C

Keep both servers running. The anonymous ping proves HTTP liveness, not database health. The diagnostic error endpoints deliberately throw exceptions but do not modify Company rows. Use them only in a local/training environment.

$apiBase = 'https://localhost:7119'
Invoke-RestMethod "$apiBase/api/diagnostics/ping"
$headers = @{ 'X-Api-Key' = (Read-Host 'Same private API key as MVC_App' -MaskInput) }
Invoke-RestMethod "$apiBase/api/diagnostics/whoami" -Headers $headers

# No key: expect 401. SkipHttpErrorCheck permits inspection of the expected error.
(Invoke-WebRequest "$apiBase/api/diagnostics/whoami" -SkipHttpErrorCheck).StatusCode

# Known failures, with a valid key so authorization does not mask the intended error:
foreach ($test in @('bad-request', 'not-found', 'conflict', 'server-error', 'unavailable')) {
    $response = Invoke-WebRequest "$apiBase/api/diagnostics/$test" -Headers $headers -SkipHttpErrorCheck
    "{0}: HTTP {1}" -f $test, $response.StatusCode
    $response.Content
}
$headers.Clear()

Expected results are ping/whoami with a key: 200; whoami without a key: 401; bad-request: 400; not-found: 404; conflict: 409; server-error: 500; unavailable: 503. Copy a real traceId from an error response into query 9. Missing/wrong keys cause 401 before the selected diagnostic executes. Wait for exporter/batch/index-refresh delays, then use the Kibana queries in section 7.

8.6 Run the API console client — optional controlled workload

The default scenario and mutation load create/update/delete Company data. Use a disposable training database, understand the generated IDs and avoid overlapping runs. Start with the read-only load below; its POST/PUT/DELETE counts are explicitly zero. The normal scenario command is a separate, optional write-producing test.

$env:MVCAPP_API_BASEURL = 'https://localhost:7119'
$env:MVCAPP_API_KEY = Read-Host 'Same private API key as MVC_App' -MaskInput
dotnet run --project MVC_App.ApiClient -- --help

# Read-only HTTP load against the configured training API:
dotnet run --project MVC_App.ApiClient -- --load --gets 20 --posts 0 --puts 0 --deletes 0 --concurrency 2 --progress 10

# Optional: full scenario, including database writes and intentional failures:
dotnet run --project MVC_App.ApiClient -- --iterations 1 --delay 250
Remove-Item Env:MVCAPP_API_KEY

This console does not export telemetry itself. Observe the resulting MVC server events in Kibana and use the console's returned trace IDs for correlation. Its local latency report is not an OTel metric stream.

This project is not needed to demonstrate ELK. It needs a separately provisioned PostgreSQL Employee schema, network/database access and an Azure Monitor destination if remote export is desired. 8.9 Troubleshooting checklist

  1. No web process starts: inspect the build output, startup exception, SDK and occupied HTTP ports. A successful Compose start does not launch either application.
  2. Login or CRUD fails: verify each database connection, SQL permissions, the Identity migration and the existing Company tables. Anonymous ping can succeed while the databases are unavailable.
  3. All API calls return 401: verify the private key and X-Api-Key header match between MVC and the caller; a valid Blazor login cookie is not an API key.
  4. No logs.jsonl growth: inspect the exporting process's effective endpoint/enable settings and Collector logs. Host processes use localhost:4318; a container cannot use its own localhost to reach another container.
  5. The file grows but no log index appears: inspect Logstash file access, offsets and parsing/mapping errors. Do not reset sincedb as the first troubleshooting step; replay can create duplicates.
  6. Indices exist but Discover is empty: check the data view, time range, query language and current filters. Use service_name rather than an unprefixed service.name; application fields are under log_attributes.
  7. A query field is unavailable: generate the relevant event first and refresh the data view's field information if needed. Do not assume a log-only field exists in the trace/metric data streams.

The smoke test answers a narrow but useful question: does the web host send all three signals when enabled, and stop sending them when disabled or unconfigured? It uses temporary loopback ports and checks nonempty protobuf payloads and service identity without database writes. You still need to check the Collector, Logstash and Elasticsearch to verify the complete ingestion path.

Do not use docker compose down -v casually: it removes the named sincedb volume and can cause retained log files to be reprocessed later. There is no configured retention lifecycle for the Elasticsearch daily log indices, so the file exporter's three-day rotation does not define Elasticsearch retention.

9. Before taking this beyond a local demo

  • Local-only security posture: Elasticsearch security/TLS are disabled and host ports are loopback-bound. Do not expose this Compose stack publicly. Production needs authenticated/encrypted ingestion, access control, durable storage, backups, retention and resource planning.
  • Rotate shared credentials. Replacing a secret with a placeholder in an article does not revoke the original. Rotate any exposed database credentials or API keys, and keep replacements out of source files and command histories.
  • Sensitive observations: request queries, SQL command text, authentication user names, exception messages and PostgreSQL salary aggregates can disclose information. Neither logging scopes nor OTel provide automatic application-specific redaction here.
  • Development TLS shortcuts: Blazor accepts any server certificate only in Development; the API client has an optional insecure switch. PostgreSQL's configured Require mode encrypts but does not validate the peer like VerifyFull. Do not copy these settings into production.
  • Loss and duplication: the Collector has bounded memory/queue/retries, the log file rotates, and Logstash lacks a configured persistent queue or deduplication ID. This is not an exactly-once or guaranteed-delivery architecture.
  • Instrumentation gaps: Blazor Identity database calls have no explicit SqlClient instrumentation/interceptor in that project; browser real-user events and circuit-wide tracing are not configured. API console statistics are not exported OTel metrics. PostgreSQL telemetry does not reach ELK.
  • Sampling and cardinality: neither web extension explicitly configures a custom sampler. Understand SDK defaults/upstream sampling decisions before assuming every trace is recorded. Keep high-cardinality user IDs, SQL text and raw URLs out of metric labels.
  • Diagnostic integrity: deliberate failure endpoints and load clients should be restricted to controlled environments. A success/failure chart containing intentionally injected errors is not a production availability measure.
  • Operational visibility: no Collector health-check extension or explicit self-observability pipeline is configured. That does not mean the Collector has no default internal diagnostics; it means this solution has not wired a monitoring strategy for the telemetry system itself.

The practical lesson is to observe the observer: investigate dropped exports, file lag, mapping failures, disk usage and retention alongside application errors.
