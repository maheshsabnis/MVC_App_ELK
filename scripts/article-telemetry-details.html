Walking through TelemetryExtensions.cs

Most of the application's telemetry setup comes together in this one method. Read it from top to bottom: first it checks configuration, then it identifies the service and chooses the signals, and finally it connects them to the Collector.

  1. Start with the namespaces. The OpenTelemetry imports make the logging, tracing, metrics, resource and exporter extension methods available. Their implementations come from the project's NuGet references. System.Data.Common has a more specific job: it supplies DbCommand for the SQL enrichment callback near the middle of the method.
  2. The extension keeps Program.cs readable. The this WebApplicationBuilder builder parameter lets startup code call builder.AddApplicationTelemetry(). Returning the builder allows further configuration to be chained. All of this runs before builder.Build(), rather than once for each request.
  3. Read the Collector address from configuration. builder.Configuration["OTEL_EXPORTER_OTLP_ENDPOINT"] gets the base URL, with the usual ASP.NET Core providers allowing environment values to override JSON. A host process can reach the local Collector at http://localhost:4318. Inside a container, however, localhost means that container; use an address the application can actually reach.
  4. Allow telemetry to be switched off. GetValue("Telemetry:Enabled", true) defaults to enabled, but an endpoint must also be present. Either Telemetry__Enabled=false or a blank endpoint makes the method return early. This skips the OTel registration here; it doesn't turn off ordinary logging providers, request middleware or diagnostic endpoints.
  5. Catch an invalid URL before serving requests. Uri.TryCreate checks for an absolute address, and the next condition permits only HTTP or HTTPS. An invalid setting raises InvalidOperationException at startup. This is a configuration check, not a connectivity test: a valid URL can still point to a stopped Collector.
  6. Connect existing ILogger calls to OTel. builder.Logging.AddOpenTelemetry adds a provider, so application logs can enter the telemetry pipeline without rewriting every ILogger<T> call. Logging filters still apply. The destination is configured later by the shared exporter.
  7. Keep the rendered log message. IncludeFormattedMessage = true makes the message readable without reconstructing it from a template and argument list. That is convenient in Discover, but it also means any sensitive argument can end up in the rendered text. Formatting is not redaction.
  8. Keep the context carried by scopes. With IncludeScopes = true, fields supplied by request middleware and the SQL interceptor travel with the log. Examples include http.response.status_code, error.category, url.path and db.duration_ms. Logstash places these under log_attributes, which is why the Kibana queries use that prefix. An active Activity can also supply trace/span IDs; startup logs and work without one may have no such correlation.
  9. Reduce duplicate SQL logging without hiding failures. AddFilter<OpenTelemetryLoggerProvider> raises the minimum level for Microsoft.EntityFrameworkCore.Database.Command to Warning on the OTel provider. Warning, Error and Critical events remain eligible. The custom MVC_App.Data.DbCommandLoggingInterceptor has a different category and still logs its commands. This filter neither changes other providers globally nor removes SQL text from spans.
  10. Let the host own the providers. builder.Services.AddOpenTelemetry() starts the shared tracing and metrics configuration and ties provider lifecycle to the application host. There is no need to construct a provider inside each controller. The remaining fluent calls specify what that shared setup should collect.
  11. Give every signal a service identity. ConfigureResource uses AddService with OTEL_SERVICE_NAME and adds deployment.environment.name. These attributes distinguish MVC_App from Blazor and Development from Production. The ?? fallback to builder.Environment.ApplicationName handles a null setting, not an empty string. Resource values describe the producer, so they are reused across requests and signal types.
  12. Observe incoming HTTP requests. Under WithTracing, AddAspNetCoreInstrumentation() collects the framework's request activities as server spans. A valid incoming trace context can connect the request to its caller. This doesn't automatically add a business span for every Razor or Blazor interaction, and recording/export still depends on sampling and SDK configuration.
  13. Observe outgoing HTTP calls too. AddHttpClientInstrumentation() collects supported HttpClient activities and propagates trace context. An outbound call made during an active request can then belong to the same trace. It only observes calls that actually happen. The Blazor client span is registered in Blazor's own extension; this MVC extension observes the receiving server request.
  14. Follow the request into SQL Server. AddSqlClientInstrumentation subscribes to the supported SQL client diagnostics. Both CompanyContext and IdentityContext use SQL Server, so their commands can be observed—not just employee and department queries. A command can inherit an active request's context, but background work won't acquire an HTTP parent on its own. Npgsql needs the separate instrumentation used in PgSqlClient.
  15. Keep exception details on failed SQL spans. options.RecordException = true asks the instrumentation to attach exception details when it observes a failure. That helps explain a failed dependency in the trace. It doesn't catch the exception for the application or decide the response status; normal propagation and ExceptionHandlingMiddleware still do that work.
  16. Notice exactly where command text is added. EnrichWithSqlCommand receives the Activity and command. After checking command is DbCommand dbCommand, it calls activity.SetTag("db.statement", dbCommand.CommandText). Parameterized SQL usually contains placeholders, but literals can still expose data. This callback neither redacts nor truncates the statement. The interceptor's 1,000-character limit applies to its log message, not to this span attribute.
  17. Use HTTP metrics for the broader picture. WithMetrics adds ASP.NET Core and HttpClient measurements such as request and dependency duration. A trace explains one operation; metrics help show whether the same behavior is common. Available instruments depend on the framework and package versions, and arbitrary log messages are not automatically turned into metrics.
  18. Check the runtime when several endpoints slow down. AddRuntimeInstrumentation() collects supported measurements for garbage collection, managed memory and the thread pool. Those observations can help distinguish one slow query from process-wide pressure. They are separate from the custom employee counters and salary gauges defined in PgSqlClient's AppDiagnostics.
  19. Subscribe to the framework meters you need. AddMeter names the Kestrel, routing and diagnostics sources: Microsoft.AspNetCore.Server.Kestrel, Microsoft.AspNetCore.Routing and Microsoft.AspNetCore.Diagnostics. It listens for their instruments rather than creating new ones. You may need to exercise the relevant behavior before a measurement appears.
  20. Send all three signals through OTLP. UseOtlpExporter(OtlpExportProtocol.HttpProtobuf, endpointUri) connects logs, traces and metrics to the Collector. This is protobuf over HTTP—not JSON or OTLP/gRPC. From the configured base URL, the exporters use paths such as /v1/logs, /v1/traces and /v1/metrics. Neither a Kibana address nor an Elasticsearch index name belongs here.
  21. Don't confuse a successful request with a successful export. The host manages the providers and their disposal; processors and readers control export timing. This method doesn't explicitly choose a sampler, durable queue, retry policy or custom metric interval. Set OTEL_METRIC_EXPORT_INTERVAL in the actual process environment, or bind it explicitly, rather than assuming the JSON key configures the reader. Shutdown and network failures can still lose telemetry, so check the pipeline beyond the application.
  22. Follow the Collector's routing for the final step. Its memory_limiter and batch processors run before export. Traces and metrics go directly to Elasticsearch OTel data streams. Logs take the rotating JSONL path through Logstash into mvcapp-logs-YYYY.MM.dd, where Kibana can query them. Keeping this routing outside the application lets you change storage and transformations without rewriting every instrumentation call.

The method's job ends at collecting and exporting the signals. To investigate a real request, combine that setup with the context added by middleware and SQL interceptors, then follow the data through the Collector to the appropriate Kibana view.
